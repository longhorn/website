## Applicable versions

- Upgrading from Longhorn v1.11.2 (or earlier) to v1.11.3 (or v1.12.1+).

## Symptoms

- During an upgrade, all `longhorn-manager` pods enter a crash-loop state and the upgrade fails. 
- The data path remains active and volumes are not impacted, but the Longhorn control plane goes down.
- The `longhorn-manager` pods display the following sequence of errors in their logs:
    ```text
    level=warning msg="Failed to parse webhook CA secret longhorn-system/longhorn-webhook-ca" func=cert.loadHealthyCA file="bootstrap.go:148" error="parse CA private key: x509: failed to parse private key (use ParseECPrivateKey instead for this key format)"
    
    level=info msg="Regenerating webhook CA and leaf for namespace longhorn-system" func=cert.EnsureWebhookSecrets file="bootstrap.go:99"
    
    level=error msg="Upgrade failed: upgrade resources failed: Internal error occurred: failed calling webhook \"mutator.longhorn.io\": failed to call webhook: Post \"[https://longhorn-admission-webhook.longhorn-system.svc:9502/v1/webhook/mutation?timeout=10s](https://longhorn-admission-webhook.longhorn-system.svc:9502/v1/webhook/mutation?timeout=10s)\": tls: failed to verify certificate: x509: certificate signed by unknown authority"
    ```

* Attempting a standard Helm rollback to the previous version (for example, v1.11.2) does not recover the cluster. The downgraded managers reuse the newly regenerated secrets, while the webhook configurations continue to trust the old CA.

## Details

In Longhorn v1.11.2 and earlier, the `longhorn-webhook-ca` secret utilized an ECDSA P-256 key generated by Rancher's dynamiclistener. Starting in v1.11.3, the in-process webhook TLS bootstrap strictly requires a PKCS#8 RSA key.

During the upgrade, the new `longhorn-manager` treats the existing ECDSA CA as unhealthy and generates a new RSA CA. However, the `longhorn-webhook-mutator` and `longhorn-webhook-validator` admission webhooks still hold the old CA in their `caBundle`. When the upgrade step attempts to write Longhorn resources through these webhooks, it fails TLS verification, causing every manager to exit and creating a deadlock.

## Pre-Upgrade Verification

Before initiating an upgrade, you can verify if your current installation is affected by inspecting the existing `longhorn-webhook-ca` secret for the legacy ECDSA key.

Run the following command:

```bash
kubectl get secret -n longhorn-system longhorn-webhook-ca \
  -o jsonpath='{.data.tls\.key}' \
  | base64 -d \
  | grep -Fx -- '-----BEGIN EC PRIVATE KEY-----'
```

If the command outputs `-----BEGIN EC PRIVATE KEY-----`, the first v1.11.3+ startup will attempt to regenerate the CA and trigger this deadlock.

## Workaround

To resolve the deadlock (or prevent it if caught mid-upgrade), you must delete the existing webhook configurations so the managers can re-register them with the newly generated CA. This is a one-time effort.

1. Delete the mutating and validating webhook configurations:
    ```bash
    kubectl delete mutatingwebhookconfiguration longhorn-webhook-mutator
    kubectl delete validatingwebhookconfiguration longhorn-webhook-validator
    ```
2. Restart the `longhorn-manager` pods to force them to re-register the configurations with the correct RSA CA:
    ```bash
    kubectl -n longhorn-system delete pod -l app=longhorn-manager
    ```
3. Verify that the new `longhorn-manager` pods start up successfully and enter the `Running` state:
    ```bash
    kubectl -n longhorn-system get pods -l app=longhorn-manager
    ```

Once the managers are running, the upgrade will proceed normally.
